Marketplace Helper App

Architecture diagram for MCP-based Zoom Marketplace app management, OAuth authorization, manifest operations, and support requests.

1 System architecture
2 Authorization flow
1

MCP client starts login

Client discovers protected-resource metadata and opens the helper authorization endpoint with PKCE.

2

Helper creates state

Signed state binds the MCP redirect, nonce, requested scopes, and PKCE challenge.

3

Zoom user consent

Browser is redirected to Zoom OAuth. The user authorizes the Marketplace Helper app.

4

Callback and exchange

Helper receives the Zoom code, exchanges it server-side, and stores the resulting token record.

5

Issue MCP tokens

Helper returns a one-time authorization code, then MCP access and refresh tokens to the client.

6

Authenticated tools

Client sends a bearer token to /mcp; the helper refreshes Zoom tokens when needed.

3 Marketplace management flow
A

Tool request

Client calls an MCP tool such as list, create, inspect, export, validate, update, or delete.

B

Manifest safety

For updates, export the current manifest, change intended fields, validate the complete replacement.

C

Create by app type

General and S2S apps use /v2/marketplace/apps. Meeting SDK is configured within a General App.

D

Zoom API response

Helper preserves upstream status and error details, including validation responses with ok:false.

E

Verify destructive work

After delete or update, read back the app or manifest to confirm the effective state.

Security and deployment boundaries

TLS at public edge Nginx reverse proxy PKCE S256 Signed OAuth state One-time codes Refresh-token rotation SQLite 0600 AES-256-GCM at rest Secrets from environment

Current implementation scope

The deployed implementation uses a public HTTPS edge, Nginx, PM2, an AES-256-GCM encrypted local SQLite database, and outbound HTTPS calls to Zoom. It does not require PostgreSQL, Docker, RTMS, Zoom Apps SDK runtime, Meeting SDK runtime, AI providers, or another third-party database.
